# Credibility and External Reference

The selected existing project is [iot-audit](https://github.com/emanuelepiodebernardis/iot-audit). It is integrated as an **offline external benchmark**, not as an unqualified live detector. Its published LightGBM pipeline is pinned to commit `e0decb975e2c3d723375f3b87f0ed50cb5b73b0c` and its expected artifact hash is:

```text
3d113987cbaf696aef336aa398a3ce17d07a34a97473dc06f2399d232fb5d3f0
```

## Reproduce the external reference

The model binary is ignored by Git. Fetch it only through the pinned command:

```powershell
python scripts/fetch_iot_audit_model.py
python scripts/evaluate_iot_audit_candidate.py
```

The fetch command rejects a changed hash, caps the download size, and writes a metadata file containing the upstream commit and source URL. The evaluator applies the exact 13-field upstream transformation to complete Zeek records and writes a report under `runtime/iot-audit-pretrained/`.

The current recorded result is a domain-shift check against real IoT-23 captures, not a positive deployment claim:

- 3,720 compatible test flows were evaluated.
- Attack recall was 91.30%.
- False-positive rate was 90.53%.
- The candidate is `eligible: false`, `live_validated: false`, and `response_eligible: false`.

That result is useful because it demonstrates a real failure mode: a model can appear strong on its training domain and still be unsafe when applied to another device/network distribution.

## What can be claimed

1. The external repository supplies a reproducible pretrained binary pipeline for its documented TON-IoT representation.
2. This repository verifies the artifact hash, serialized pipeline shape, class contract and feature order before loading it.
3. The pipeline can be evaluated offline on complete recorded Zeek flows.
4. The existing promoted lab model can classify binary traffic for the registered ESP32, its current Wi-Fi topology and `scapy-lab-flow-v1`, subject to its evidence report.

## What cannot be claimed

- The upstream model detects arbitrary ESP32 attacks live.
- An offline cross-dataset result proves protection on another device or network.
- A binary score identifies a specific attack family.
- Application block records prove a gateway blocked the attacker.
- A manual OLED/LED/buzzer test proves model-triggered hardware response.

## Evidence package for a presentation or review

Run the following after an experiment:

```powershell
python scripts/build_credibility_report.py `
  --output runtime/credibility/report.json `
  --markdown runtime/credibility/report.md
python -m unittest discover -s tests -v
python -m compileall -q backend scripts ml
```

The report records the Git revision, model hashes, upstream commit, model status, dataset/model scope, and a claim ledger. The dashboard's **Models** page reads the same report and displays the status instead of presenting all models as equivalent.

For credible live-protection claims, add independent labelled captures from multiple owned devices and days, keep training/validation/test captures disjoint, use the identical extractor in training and runtime, measure recall and false-positive rate per device and family, and verify gateway enforcement separately. Until then, use the exact scope wording generated by the claim ledger.
